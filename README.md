# 长跑型 Agent 运维体系设计记录

> **English version** → [README.en.md](README.en.md)

**这是一套给"长期在自有机器上跑编码 agent"的运维体系设计记录。** 八份文档分别回答八个问题：**多台工作机之间怎么交接状态**、**单机环境需要哪些自治能力**、**一整套"角色分工 + 家规纪律"长什么样**、**一次性能排查的错误归因是怎么被自己的复测推翻的**、**一份方案在开工之前该被怎么审**、**一块只读监控面板该回答什么、以及它绝不做什么**、**一个已经建好的自动化能力要满足什么条件才敢真的放开让它动手**、**一套几十份文档的体系该怎么被审出"说明书和机器已经对不上"**。

它们记录的不是"我们的系统长什么样"，而是**做这类系统时踩过哪些坑、怎么判断、怎么兜底**——文中所有结论都来自真实事故与实测数据，包括那些**被实测推翻、原样保留在正文里的错误口径**（`05` 整篇就是这件事的完整过程）。

---

## 这套体系在解决什么问题

如果你在做下面这些事，这批文档大概率对你有用：

- 在一台（或两台、三台）自己的工作机上**长期跑编码 agent**，不是跑单个任务就销毁的沙箱；
- 遇到过这些症状：**会话把自己写坏** · **任务队列悄悄卡死** · **插件一更新启动就崩** · **备份任务把另一台机器的工作覆盖掉** · **换机器时状态丢一半**；
- 想做任何"**让 agent 自己盯自己**"的事，但必须先回答：**哪些可以无人值守地自动干？哪些必须问人？事后怎么证明它没干错？**

**通用的"网页服务运维"经验在这里不能直接套用**：故障面是会话文件、加密的单文件状态、厂商 SDK 的破坏性变更，以及一个更根本的现实——**这套系统的使用者可能只有一个人，所以你永远攒不够样本量去相信自己的规则**。这批文档把"我们无法确定它准不准"当成**设计输入**，而不是拿去粉饰的东西。

## 怎么读

- **只想知道"多机怎么交接"** → 直接读 `01`。
- **想设计自己的运维管家** → 先读 `02` 的 §4（宪法：对象三型 + 自治光谱）与 §5（安全 / 并发 / 可观测），再看 §6 各能力域。
- **想先看"这套东西最后长成什么样、凭什么敢让它自动跑"** → 直接读 `03`：班底分工、五层架构、**八条家规**（每条都写了"为什么立 / 怎么判 / 代价是什么"）、一张把**四套 L 编号**摊开对照的表，以及几条**用实测钉死的硬约束**（认证门与存活判据的冲突、账本独占锁、单实例的并发容量）。
- **想抄具体判据** → `03` §4 的 R6（打扰预算 / 隐私边界 / 远程降级 / 入口最小面）每条都带"阈值 / 权威源 / 取证方式 / 留痕处"——**判据只有能被核对才算判据**，这套表格可以直接改造成你自己的。
- **想知道"结论写错了以后怎么办"** → 读 `05`。它是这批文档里唯一**整篇都在演示自我更正**的一篇：错误归因、复测证据、"0.8% 解释不了 110%"的当场推翻、以及"改对了东西但没解决原问题"的记账，全部原样留在正文里——**它不是成功案例，是一次归因翻车后怎么收场的过程记录**。
- **想审自己的方案** → 读 `04`：五轮视角（工程契约 / 实现者 / 运行期 / 横切四表 + 五环 / 前提实证）+ 一道落地后对标闸门，附选轮矩阵、审核前三件取证、九条反模式与一页速查卡。
- **想给自己的 agent 做一块只读面板** → 读 `06`：它该回答什么（不是"服务在不在"，而是"今天怎么样、哪些东西静默坏了"）、**显示纪律**（读不到就显示「不可探测 + 原因」，绝不显示 0、绝不显示假绿）、**取数工程**（分片 / 进程内 TTL 缓存 / 单飞 / 超时预算 / 局部降级）、以及**面板与真源的关系**（只渲染不复算）。最后一节是"**什么该砍**"，那节的价值不低于任何一张图。
- **想放开一个自动化动作、又怕它乱来** → 读 `07`：它给的不是"该不该自动"的态度，而是一条**从建好到敢开**的流程——门槛怎么算（为什么用跨机并集取样本、却按机放行）、**动作 → 风险级 → 开关 → 护栏 → 放行判据**这张矩阵怎么读、放行当天只做"改表 + 留痕"、放行后 48 小时怎么对账，以及怎么防止"观测到一半尺子被改"。第七节的限度声明同样值得先看。
- **想知道自己那套文档还准不准** → 读 `08`：一套长期演进的文档体系里，**过期 / 冲突 / 无人定义**三类问题该怎么查——先取实况再读文档、四张横切对照表、问题分四档、以及"回写纪律"。它最有用的一句是：**造出来的东西往往是好的，烂的是说明书**。
- **想让长会话"自己交班"** → 读 `09`：它不讲"该不该自动"，而讲一次交接要过哪些闸门、**哪一步最容易静默失效**——三个载体谁是权威源、标题轴为什么值得当成一个有规范的工程对象（含一次 59 毫秒丢轴的完整定位与修法）、**权限为什么必须两段断言**、以及"**没有明确的下一步就不许开新会话**"这条止损线。第 12 节的"明确不做"与第 14 节的"未实测项"同样值得先看。
- **`02` 与 `03` 的关系**：`02` 是**设计快照**（记录"当初怎么想的"，含当时未验证的假设），`03` 是**更新后的全景**（记录"现在长什么样"）。两份**互不替换**，`02` 头部有指向行。
- **想知道"这些文档有多可信"** → `01`–`03` 三份设计稿的末尾都有「审核意见落实记录」与「假设与验证时机」两节：前者是**多少个视角挑出多少条问题、落在哪**，后者是**哪些结论还没被验证、验证失败怎么退**。**没有这两节的设计稿，一律按"作者的自我感觉"打折看。**（`04` 是**审核规程本身**、`05` 是一份**实测记录**、`06` 是一份**设计纪律**、`07` 是一份**判据稿**、`08` 是一份**审核记录**、`09` 是一份**机制方法论 + 实测记录**，都不属于"被审的设计稿"，故不带这两节。）

## 三条阅读提示

1. **占位符**：文中 `<工作区根>`、`<DSH 主目录>`、`A 机 / B 机 / C 机`、`steward-*` 等均为占位名；模型名与第三方服务名仅示意，替换为读者自有渠道即可。
2. **数字**：文中所有实测数字（文件数、体积、耗时、条数、并发容量）都来自一次或多次真实观测，**它们是"当时的事实"，不是设计参数**——参考其量级与判断方式，不要照抄阈值。
3. **语气**：原稿是内部设计稿，保留了"这里原来写错了、后来改成这样"的修订痕迹与反驳意见。这是刻意保留的——**设计稿的价值往往在于"为什么否决了另一个方案"**。

## 语言与翻译

| 内容 | 语言 | 原因 |
|---|---|---|
| README、仓库描述、发布说明 | **中英双份** | 让国际读者在投入时间之前就能判断"这份文档跟我有没有关系" |
| 九份文档（01 / 02 / 03 / 04 / 05 / 06 / 07 / 08 / 09） | **中文为原文**；英文**按需单篇翻译** | 千行设计稿的忠实翻译是一份需要长期维护的第二成品——全量提前翻译，结局通常是"要么两份都烂掉，要么因为有译文而不敢更新原文" |
| 组件仓 README | **英文必备** | 组件 README 是它的用户界面，篇幅短，而且是陌生人读到的第一份东西 |

**翻译怎么落地**：英文版以 `XX-<名称>.en.md` 的形式**新增在中文件旁边**（绝不替换原文），两个 README 互相链接，中文文件始终是唯一权威源。需要哪份设计稿的英文版，**开 issue 指名**即可——需求本身就是排期信号。

## 仓库拓扑与组件（后续会陆续开源）

本仓是这套体系的**文档仓**；实现它的各个组件会**分仓陆续开源**（每个组件一个仓，而不是全塞进本仓）：

```
ops-handoff-design   【文档仓】 ← 本仓：方法论与设计稿（唯一权威叙述）
dsh-*                【组件仓】 ← 每个组件一仓，各自的 README 回链到本仓的对应章节
```

**为什么要分开**：文档读者不一定装插件、插件用户不一定读方法论；而且**两边的许可证是刻意分开的**（文档 CC BY-NC-SA 4.0 防商业套利；代码侧主许可为 AGPL-3.0，并另提供商业授权）——放在一个仓里容易被误读成一回事。

- **组件的完整清单（含状态与设计依据）** → 见 [`发布说明.md` §4.5 组件索引表](发布说明.md)。
- **组件仓的作者请注意**：新增一个组件仓时，请照 `发布说明.md` §4.3 的模板在其 README 加「设计依据」节，并回索引表补一行。
- **什么组件不该开源** → 见 `发布说明.md` §4.6（准入四条 + 反面清单）。
