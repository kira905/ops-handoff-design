## 这是什么

把两套已经跑在生产环境的**运维体系设计稿**脱敏后公开——它们记录的不是"我们的系统长什么样"，而是"做这类系统时踩过哪些坑、怎么判断、怎么兜底"。

**背景一句话**：这是给"长期在一台（或两台）工作站上跑编码 agent、并且越跑越重"的场景设计的运维体系——会话会坏、任务会堆、插件会崩、备份会互相覆盖、换机时会丢状态，而这些问题的解法和"网页服务运维"差别很大。文中所有结论都来自真实事故与实测数据。

| 文件 | 内容 | 原稿规模 |
|---|---|---|
| [`01-多机交接与云中继设计.md`](01-多机交接与云中继设计.md) | 多台工作机之间如何**无缝交接**（离开时交出去、到达时接过来并落到生产路径），以及一台云服务器如何同时承担「固定入口 / 活跃机登记 / 交接中继」三角色 | 700 行设计稿 + 四轮审核 67 条意见登记 |

## 怎么读

- **只想知道"多机怎么交接"** → 直接读 `01`。
- **想设计自己的运维管家** → 先读 `02` 的 §4（宪法：对象三型 + 自治光谱）与 §5（安全 / 并发 / 可观测），再看 §6 各能力域。
- **想知道"这两份文档有多可信"** → 每份末尾都有「审核意见落实记录」与「假设与验证时机」两节：前者是**多少个视角挑出多少条问题、落在哪**，后者是**哪些结论还没被验证、验证失败怎么退**。**没有这两节的设计稿，一律按"作者的自我感觉"打折看。**

## 三条阅读提示

1. **占位符**：文中 `<工作区根>`、`<DSH 主目录>`、`A 机 / B 机`、`steward-*` 等均为占位名；模型名与第三方服务名仅示意，替换为读者自有渠道即可。
2. **数字**：文中所有实测数字（文件数、体积、耗时、条数）都来自一次或多次真实观测，**它们是"当时的事实"，不是设计参数**——参考其量级与判断方式，不要照抄阈值。
3. **语气**：原稿是内部设计稿，保留了"这里原来写错了、后来改成这样"的修订痕迹与反驳意见。这是刻意保留的——**设计稿的价值往往在于"为什么否决了另一个方案"**。

## 仓库拓扑与组件（后续会陆续开源）

本仓是这套体系的**文档仓**；实现它的各个组件会**分仓陆续开源**（每个组件一个仓，而不是全塞进本仓）：

```
ops-handoff-design   【文档仓】 ← 本仓：方法论与设计稿（唯一权威叙述）
dsh-*                【组件仓】 ← 每个组件一仓，各自的 README 回链到本仓的对应章节
```

**为什么要分开**：文档读者不一定装插件、插件用户不一定读方法论；而且**两边的许可证是刻意分开的**（文档 CC BY-NC-SA 4.0 防商业套利，代码 MIT 降低使用门槛）——放在一个仓里容易被误读成一回事。

- **组件的完整清单（含状态与设计依据）** → 见 [`发布说明.md` §4.5 组件索引表](发布说明.md)。
- **组件仓的作者请注意**：新增一个组件仓时，请照 `发布说明.md` §4.3 的模板在其 README 加「设计依据」节，并回索引表补一行。
- **什么组件不该开源** → 见 `发布说明.md` §4.6（准入四条 + 反面清单）。
